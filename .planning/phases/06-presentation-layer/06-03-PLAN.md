## Objective

Implement both Application-to-Presentation mappers — the error mapper (pure transform with hybrid variant detection) and the result mapper (with try/catch safety guarantee). These are the core bridge between the OOP Application layer and the DU Presentation layer.

> **Import boundary:** Presentation imports from Application + Kernel only — no Domain or Infrastructure imports allowed.

<action>
Implement `application-to-presentation-error.mapper.ts` with:

1. **`mapApplicationToPresentationError` function** with signature:
   ```typescript
   function mapApplicationToPresentationError(
     appError: ApplicationError,
     options?: { userMessageOverrides?: Record<string, string> }
   ): PresentationError
   ```

2. **Hybrid detection logic** (D-11):
   - Check `instanceof CommandValidationError` → return `createValidationError(appError.code, commandValidationError.fieldErrors)`
   - Check `instanceof AuthorizationFailedError` → return `createAuthorizationError(appError.code, getUserMessage(appError, options))`
   - Check if `appError.code` starts with `NOT_FOUND_` → return `createNotFoundError(appError.code, getUserMessage(appError, options))` (D-17)
   - Fallback duck-type detection: if `appError` has a `fieldErrors` property → `ValidationError`; if `appError` has a `reason` property → `AuthorizationError`
   - Catch-all: return `createSystemError(appError.code, getUserMessage(appError, options), 'error')` (D-12)

3. **`auto-user-message` helper**: Generate user-safe message from `appError.message` by removing internal details (heuristic: truncate at first parenthesis or colon if technical).

4. **`userMessage` override**: If `options.userMessageOverrides[appError.code]` exists, use that instead of auto-generated message.

**Note:** No try/catch in this mapper — it throws on truly impossible states per D-15. The error mapper deals only with `ApplicationError → PresentationError` transform; `operationId` generation belongs in the result mapper (Task 2).
</action>

<acceptance_criteria>
- `mapApplicationToPresentationError` exists and returns `PresentationError`
- AuthorizationFailedError → AuthorizationError variant
- CommandValidationError → ValidationError variant with fieldErrors preserved
- Errors with code starting with `NOT_FOUND_` → NotFoundError variant
- Unknown errors → SystemError variant (catch-all)
- `npx tsc --noEmit` passes
</acceptance_criteria>

<action>
Implement `application-to-presentation-result.mapper.ts` with:

1. **`mapApplicationToPresentationResult` function** with signature:
   ```typescript
   function mapApplicationToPresentationResult<T>(
     appResult: ApplicationResult<T>,
     params: { operationName: string },
     options?: { userMessageOverrides?: Record<string, string> }
   ): PresentationResult<T>
   ```

2. **Logic** (D-15 hybrid safety):
   - Wrap entire body in try/catch
   - Import `createOperationId` from Kernel (`@/Core/Kernel/Primitives/Types/operation-id.type`) and generate `operationId` string: `createOperationId(params.operationName)`
   - If `appResult.isSuccess` → return `{ _tag: 'Success', data: appResult.data, operationId }`
   - If `appResult.isFailure` → call `mapApplicationToPresentationError(appResult.error, options)`, return `{ _tag: 'Failure', error: mappedError, operationId }`
   - In catch: return `{ _tag: 'Failure', error: createSystemError('MAPPER_ERROR', 'An unexpected error occurred', 'critical'), operationId }`

> **Note:** `appResult.data` is typed as `T | undefined` (from `ResultBase`). At runtime, Success always has data, but the type system reflects the union. If `data` is undefined at runtime, it will be serialized correctly — no special handling needed.
</action>

<acceptance_criteria>
- `mapApplicationToPresentationResult` exists and returns `PresentationResult<T>`
- Success path returns `{ _tag: 'Success', data, operationId }`
- Failure path returns `{ _tag: 'Failure', error: PresentationError, operationId }`
- Mapper never throws — all errors caught and mapped to SystemError
- `npx tsc --noEmit` passes
</acceptance_criteria>
