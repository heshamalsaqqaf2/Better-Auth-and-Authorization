<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DomainError → mapper → ApplicationError | Error data crosses from Domain to Application layer |
| ApplicationError → serialization consumer | Error objects serialized by toJSON() for external boundaries |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-06 | Information Disclosure | Domain→Application mapper | mitigate | Mapper passes domainError code/message through as-is (D-24); no additional internal context added to error messages. DomainError already manages its own information exposure |
| T-04-07 | Information Disclosure | Specific error codes | mitigate | Error codes are semantic identifiers (USE_CASE_EXECUTION_ERROR, AUTHORIZATION_FAILED, COMMAND_VALIDATION_ERROR) — not stack traces, config values, or internal paths |
| T-04-08 | Information Disclosure | AuthorizationFailedError.reason | mitigate | `reason` string exposes failure rationale ("insufficient permissions") — this is intentional for debugging. If sensitive reasons are needed, the Presentation layer (Phase 6) mapper will sanitize |
| T-04-09 | Tampering | command-validation.error.ts fieldErrors | accept | `fieldErrors: Record<string, string[]>` is data from a validation pass — not attacker-controlled in error construction. If construction is upstream, the caller controls field names |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | No external packages used in this plan — pure TypeScript only |
</threat_model>
